# Implementation decisions

The five supplied designs are requirement evidence, not instructions to provision infrastructure or contact anyone. Hosting remains the user's responsibility.

1. React + Express 5 + PostgreSQL + MongoDB. Express keeps UI, simulator and contract validation in JavaScript. Four route/service modules retain component boundaries. PostgreSQL owns identities, inventory, workflow, audit and durable jobs; MongoDB owns flexible evidence.
2. Component design camelCase APIs supersede older system-design snake_case examples. Device creation is POST /api/v1/rooms/{roomId}/devices (201). Event source, confidence and correlationId are validated.
3. Duplicate conflict: the API tables say 409 duplicate, but pseudocode, invariants and acceptance checks require idempotency. Identical normalized content returns the original event/result (202); conflicting reuse of eventId or idempotency key returns 409. Keys are tenant-scoped. Payload property order is irrelevant.
4. Alert state table is authoritative over abbreviated storyboards: ACTIVE -> ACKNOWLEDGED -> INVESTIGATING -> RESOLVED, with escalation from the first three states and resolution from ESCALATED. No direct ACKNOWLEDGED -> RESOLVED. A new matching event after resolution creates a new alert (explicitly permitted by the design); a user cannot manually reopen old evidence.
5. unusual_sound is MEDIUM for confidence 0.75–0.89 and HIGH for >=0.90. human_help_sound >=0.85 is HIGH; smoke_alarm is deterministic CRITICAL; normal_appliance_sound is retained without an alert. Group by house/device/type within the documented windows, using acceptance time to handle delayed events consistently.
6. AI scope (superseded by 17): originally simulated labeled events and explicit rules only. Simulator events still use this path and are labelled simulated or rule based.
7. Cross-store safety: commit a PostgreSQL staging envelope/job before Mongo insert, then finalize the normalized reference/alert transaction after Mongo succeeds. This adds a durable intent before the document's Mongo-first sequence, avoiding an unrecoverable orphan when SQL is unavailable. Retries upsert immutable Mongo evidence and never repeat alert triggers. Staging payload is cleared after success; expired routine evidence is not reconstructed.
8. Local substitutes: expiring signed sessions instead of Cognito, authenticated HTTP simulator instead of IoT Core/MQTT, PostgreSQL jobs instead of SQS, simulated delivery records instead of SNS, local health instead of CloudWatch. No AWS services are provisioned. Leaflet/OpenStreetMap tiles require internet; the house table works without tiles.
9. House owners can view and acknowledge assigned houses; technicians manage inventory; responders manage alert response; operators manage their tenant and data operations. No implicit global staff bypass. Cross-tenant administration and production IAM remain deferred.
10. Default heartbeat timeout 45 seconds, accepted ingress age 24 hours, future skew 60 seconds, query window <=31 days, page size <=100, request payload <=64 KiB. Archived houses/rooms require children to be archived first.

11. Rule tables are data. `ALERT_RULES`, `COMMANDS` and `DEVICE_TYPES` in domain.js drive validation, `classify()`, `GET /api/v1/catalog`, the simulator outcome preview and the command menu, so none of them can drift. A parity test compares the preview with `classify()` at every 0.01 confidence step.
12. UI redesign (docs/UI_DESIGN.md). Kept the team's Hearth name, navy palette and fonts. Every status shows text, a shape and a color. Browser prompt/confirm dialogs were replaced by labelled dialogs that explain the effect. Raw JSON is behind "Show raw record". Severity and alert state use different shapes so they are not read as two severities.
13. House health keeps rule B-D-02 (only critical/high overrides). The overview's attention list additionally includes healthy houses with an open medium alert, so a house with an open alert is never described as "all clear".
14. Session token in sessionStorage (cleared when the tab closes) so a page reload during a demo keeps the session. No operational data is stored in the browser.
15. `worker_cursor` moved from a per-second runtime CREATE TABLE into migration 002; `live_events` rows older than LIVE_EVENT_RETENTION_HOURS (default 24) are pruned once the heartbeat cursor has passed them.
16. `GET /dashboard/preferences` returns `saved:false` with defaults when nothing is stored, so the map can fit to the houses instead of a fixed center.

17. Real AI component. The team's trained classifier (Models/my_yamnet_human_model.keras, Human_model.ipynb) runs in a separate Python service (ml/) because TensorFlow and YAMNet are Python. The Node API calls it; browsers never do. The model names the sound; AI_LABEL_MAP turns the name into an existing event type (crying -> human_help_sound; cough and breathing -> unusual_sound; the rest -> new normal_activity_sound), and ALERT_RULES decide alerts from the model's confidence. **Confirm the mapping with the team**, especially whether breathing should alert.
18. Only server-side inference can create events with source "model"; POST /events still accepts only device or simulator sources. Model events go through the same idempotent storeEvent() as other events, and their provenance (model name, version, SHA-256, probabilities, latency) is stored in MongoDB ai_results.
19. Inference failure does not create an UNKNOWN event (C3 §2.2 suggests a fallback label). Audio is not stored, so an UNKNOWN event would lose the evidence; instead the API returns 503 and the device keeps the clip and retries with the same X-Event-Id. Failures are logged in ai_inferences and visible on the AI models page.
20. Model management is per tenant (ai_model_settings): an operator enables, disables or pins a version for their community only, audited. Model files are deployed with the image, not uploaded through the UI, because a model file should go through review. The registry verifies each file's SHA-256 against its manifest and loads Keras with safe_mode.
21. Reported accuracy is shown with a caveat: 303 of 688 training rows are duplicates and the split was by row, so the notebook's 91% is an upper bound. ml/evaluate.py with --exclude ml/training-recordings.txt measures held-out accuracy; its result appears on the model card. The appliance notebook's model is not deployed: no model file was provided and its evaluation includes test data in training.
22. Ownership: the AI adapter, model management and mapping sit with Alert tracking (Kavya), whose design defines the classifier adapter; provenance storage sits with Data (Srija). The team should confirm this split.
23. Deliberate 5xx API errors keep their message (for example the retry guidance); only unexpected crashes are replaced by the generic message.

Milestones: (1) contracts/schema/security, (2) inventory and event-to-alert pipeline, (3) integrated UI/live map/simulator/data operations, (4) tests and component demonstration handoff. No cloud rollout is part of these milestones.

Implementation references: [Express async errors](https://expressjs.com/en/5x/guide/error-handling/), [PostgreSQL driver transactions](https://node-postgres.com/features/transactions), [MongoDB indexes](https://www.mongodb.com/docs/drivers/node/current/indexes/).
